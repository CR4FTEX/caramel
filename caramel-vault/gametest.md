# Game tests

Caramel's server game tests start a headless Minecraft test server with every data pack loaded, run the tests, and exit. The tests live in `src/gametest/java/io/github/cr4ftex/caramel/gametest/`, as a separate mod `caramel-gametest` (`src/gametest/resources/fabric.mod.json`). Checked with Loom 1.18.2 and Fabric API 0.161.

## How they run

- `configureTests` in `build.gradle` creates the `gametest` source set, the `gameTest` run config and the `runGameTest` task, and makes `check` depend on it. So `./gradlew build`, and CI, run every game test; `./gradlew runGameTest` runs them alone.
- `runGameTest` never counts as up to date: a second `./gradlew build` of an unchanged tree starts the test server again and runs every test ("2 executed, 10 up-to-date", with `:runGameTest` among the executed; scratch copy).
- The run inherits the `server` run config, adds `-Dfabric-api.gametest`, and works in `build/run/gameTest`, which is not cleared between runs.
- Tests are found through the `fabric-gametest` entrypoint: public, non-static, `void` methods annotated `@net.fabricmc.fabric.api.gametest.v1.GameTest` taking one `GameTestHelper`.
- Fabric names a test `<mod id>:` followed by its class's simple name and method name joined by `_`. It inserts `_` only between a lowercase letter and a capital, then lowercases the result (`TestAnnotationLocator$TestMethod.camelToSnake`): `threeBlocksInAnLMakeFourStairs` becomes `caramel-gametest:stairs_recipe_game_test_three_blocks_in_an_lmake_four_stairs`.
- With no filter, the server runs every registered `test_instance` not marked `manual_only` (`GameTestServer.evaluateTestsToRun`): Caramel's `@GameTest` methods and vanilla's `minecraft:always_pass` (`data/minecraft/test_instance/always_pass.json`, `required: false`). "All N required tests passed" counts every test run, optional ones included (`MultipleTestTracker.getTotalCount`), so N is one more than Caramel's tests.
- The exit code is 0 when all pass, the number of failed required tests otherwise (`MultipleTestTracker.getFailedRequiredCount`), 255 when the data packs fail to load (WARN "Failed to load vanilla datapack, bit oops") or a filter matches nothing, and 1 when the server crashes (`GameTestServer.onServerCrash`). Any non-zero exit fails the build.
- `GameTestHelper.fail` throws (each overload ends in `athrow`, `javap -c`), so a test stops at its first `fail`, and the server still runs every other test: a run with 6 failures logged "62 GAME TESTS COMPLETE" and each failing test's message (run log). Most of Caramel's checks collect their failures and fail once through `RecipeTestSupport.report`, as "N of M <what> failed:" and the failure lines, each naming its recipe or item, in the order the check walks (recipe id order in `MorePerCraft`, whose `packFiles` fills a `TreeMap`). `MorePerCraft.allFound` joins every line into one `fail`, with no count. One build can carry several deliberate breaks, each on a different item.
- Fabric's runner reads three more system properties (`FabricGameTestRunner.runHeadlessServer`, fabric-gametest-api-v1 4.0.32). `fabric-api.gametest.filter` runs only the tests whose ids match a pattern, `fabric-api.gametest.report-file` writes a JUnit-style XML report to that path, and `fabric-api.gametest.verify` runs each matching test several times. They go on the run in `build.gradle`: `loom { runs { named("gameTest") { property("fabric-api.gametest.filter", "caramel-gametest:*fuel*") } } }` logged "Will run tests matching caramel-gametest:*fuel* (N tests)", N being the number of test ids that match (scratch copy).
- The test classes stay out of the mod jar (`unzip -l` on it lists none).
- The test mod can register test-only content through its own `main` entrypoint: `OtherModStairs` registers a stand-in modded stairs. It exists only in game tests: `runClient`'s classpath holds main and client and not `gametest` (printed from the `runClient` task).

## The EULA

`net.minecraft.server.Main` still reads `eula.txt` and writes `eula=false` into `build/run/gameTest/eula.txt`. Fabric's gametest `MainMixin` makes the check pass while `-Dfabric-api.gametest` is set; nothing accepts the EULA. The owner chose this path, as recorded in C-001 in `docs/DESIGN.md`.

`configureTests` keeps `eula = false` and `enableClientGameTests = false`. With client game tests on, Loom's `eula = true` registers `acceptGameTestEula`, which writes `eula=true` into `build/run/clientGameTest/eula.txt` (`FabricApiTesting.configureTests`, Loom 1.18.2).

## Expected values

A test that takes its expected values from the merged data passes silently, because it checks Caramel against itself. Vanilla's own values have two sources:

- Data: `RecipeTestSupport` opens `server.getPackRepository().getPack("vanilla")` and parses the vanilla recipe files (`vanillaVariants`, `vanillaRecipes`), or lists one pack's files in one namespace (`packFiles`). Each idea's test class (`StairsRecipeGameTest` for C-001, `SlabsRecipeGameTest` for C-002, `PressurePlatesAndCarpetsGameTest` for C-003, and `FencesRecipeGameTest` for C-004, `FenceGatesRecipeGameTest` for C-005, `DoorsAndTrapdoorsGameTest` for C-006, `ButtonsRecipeGameTest` for C-007 and `WallsRecipeGameTest` for C-008, which run the checks shared in `MorePerCraft` over a `MorePerCraft.Scope`) builds its expectations from it. `MorePerCraft` takes shaped recipes, and shapeless ones of 1 to 3 ingredients laid in one row. `ShapelessRecipe` has no public getter for its ingredients in 26.3; `placementInfo().ingredients()` returns them, or an empty list when any ingredient is empty (`PlacementInfo.create` returns `NOT_PLACEABLE`, `javap -c`). `DoorsAndTrapdoorsGameTest` also builds the expected iron and copper recipes from vanilla's: the wooden counterpart's pattern, filled with the block that 9 of vanilla's ingot craft into. `WallsRecipeGameTest` reads the stonecutter's options for each block as the stonecutter menu lists them, with `RecipeManager.stonecutterRecipes().selectByInput(stack)`: `StonecutterMenu.setupRecipeList` makes that call through `level.recipeAccess()`, and `ServerLevel.recipeAccess()` returns the server's `RecipeManager` (`javap -c` on both classes). `VanillaOverridesGameTest` checks the vanilla recipe, advancement and trade ids the ideas touch, `CraftedFuelGameTest` which items have new fuel (C-001, C-003, C-004, C-006 and C-007), and `UnlockAdvancementsGameTest` the unlock advancements of Caramel's own recipes.
- Caramel adds its own stairs, slabs, walls and more to vanilla's tags (C-010, [[blocks]]), so a tag no longer lists vanilla's items alone. `RecipeTestSupport.vanillaVariants`, the walk of `#minecraft:stairs` and `#minecraft:slabs` that C-001 and C-002 compare with vanilla's recipe files, skips every item outside the `minecraft` namespace. Without that, the stairs walk, which needs a vanilla recipe for every item, stopped 10 tests with "The vanilla data pack has no caramel:recipe/honed_stone_stairs.json" (C-010's first build).
- Item components: `RecipeTestSupport.vanillaComponents` reads vanilla's default fuel and compost chances from `BuiltInRegistries.DATA_COMPONENT_INITIALIZERS.build(...)`; [[fuel]] says why they are vanilla's.

## Testing an item

`ChiselGameTest` and `ChiselRecipesGameTest` check C-009's Chisels. Their expected values are vanilla's own pickaxe, axe and hoe of each tier, the vanilla data pack, and the owner's cycles from `docs/DESIGN.md`, written out again in `ChiselGameTest.CYCLES`.

- A stack answers for its components with no world: `stack.getDestroySpeed(state)`, `stack.isCorrectToolForDrops(state)`, `stack.get(DataComponents.TOOL)`, and `stack.get(DataComponents.ATTRIBUTE_MODIFIERS).compute(attribute, base, EquipmentSlot.MAINHAND)` for attack damage and speed. `chiselsMineWhatAxesAndPickaxesMineAtHalfSpeed` runs the first two over every block in the registry, 9009 checks for the 7 tiers.
- `helper.makeMockPlayer(GameType)` gives a player that is never ticked. The game puts a held stack's modifiers on a living entity when its equipment changes during a tick, so a mock player's attributes hold none of them, an enchantment's included. `ChiselGameTest.miningSpeed` adds them with `ItemStack.forEachModifier(EquipmentSlot.MAINHAND, ...)`, reads `player.getDestroySpeed(state)`, and removes them.
- A mock player is off the ground, which divides its mining speed by 5 (`Player.getDestroySpeed`). The tests compare one speed with another, never with a number.
- `helper.useBlock(pos, player)` runs the block's own use and then the held stack's `useOn`, which reaches the block transformer. A SURVIVAL mock player's tool loses durability, so `aPlayersChiselCarvesOneStepAClick` checks the block and the wear after each click.
- `helper.useBlock` never checks an item cooldown, which the game's own block click does (`ServerPlayerGameMode.useItemOn`), so a test player keeps carving on every call. `aChiselWaitsASecondAfterEachChange` reads the wait instead, with `player.getCooldowns().isOnCooldown(stack)`, and moves it on with `player.getCooldowns().tick()`, since a mock player is never ticked.
- `UseBlockCallback.EVENT.invoker().interact(player, level, hand, hit)` asks Fabric's block-click event what it answers, as the game does before its own handling of a click. `aWaitingChiselHoldsTheClickOnBlocksItWouldChange` starts a cooldown with `player.getCooldowns().addCooldown(stack, ticks)` and reads which blocks a Chisel changes from a Chisel that is not waiting, clicked through `helper.useBlock`.
- A `makeMockPlayer` player keeps its cooldowns locally. A `makeMockServerPlayer` player has no connection, and its cooldowns send a packet when one starts (`ServerItemCooldowns.onCooldownStarted` calls `player.connection.send`), so a change that starts a cooldown on it would throw (read in the decompiled classes, not run).
- `level.setBlock(pos, state, Block.UPDATE_SKIP_ALL_SIDEEFFECTS)` places any block with no neighbour updates, drops or `onPlace`. `chiselsStripLikeAxesAndCycleTheOwnersBlocks` places every block in the registry in turn, 1359 states with each block that has an axis, such as a log, also on its side, and asks each transformer entry's `blockStateProvider().value().getOptionalState(level, random, pos)` what it gives. For each change it also checks the entry's sound, particles, durability cost, faces and loot.
- `CreativeModeTabs.tryRebuildTabContents(features, false, registries)` fills the creative tabs on a server, Fabric's `modifyOutputEvent` listeners included, and `getDisplayItems()` then lists a tab in order.
- A recipe of any type encodes to JSON with `Recipe.DIRECT_CODEC`, and `result.id` there names what it makes, for the types that have a result. `ChiselRecipesGameTest` reads loaded recipes that way.
- A menu works on a server with no screen. `ChiselGameTest.anvilEnchants` builds `new AnvilMenu(0, player.getInventory())`, sets the input slots, calls `createResult()` and reads the result slot, which is what an anvil would offer that player.
- `makeMockPlayer(GameType.CREATIVE)` overrides `gameMode()`, and `isClientAuthoritative()` to false, but never sets its abilities, unlike `makeMockServerPlayer`, which calls `gameType.updatePlayerAbilities`. `hasInfiniteMaterials()` reads `abilities.instabuild`, so an anvil treats the mock player as a survival player, silently. `GameType.CREATIVE.updatePlayerAbilities(player.getAbilities())` gives it creative's abilities.
- A server reads translations, vanilla's `assets/minecraft/lang/en_us.json` (`Language.loadDefault`) and each mod's through Fabric's server `LanguageMixin`, so `Language.getInstance().has(key)` works in a test. It never reads `sounds.json`. `FabricLoader.getInstance().getModContainer(Caramel.MOD_ID).flatMap(mod -> mod.findPath("assets/caramel/sounds.json"))` reads that file as the mod ships it: `configureDataGeneration` in `build.gradle` puts `src/main/generated` on the main resources, so the generated assets are there.
- `packFiles(helper, Caramel.MOD_ID, Caramel.MOD_ID, registry)` reads Caramel's own files in its own namespace. `chiselRecipesUnlockAndListLikeTheirPickaxes` compares each Chisel recipe's unlock criteria and recipe book category with the vanilla pack's files for the tier's pickaxe.

## Testing blocks

`StoneFamilyGameTest` checks C-010's blocks; their expected values are vanilla's closest blocks, the vanilla data pack and the owner's rules in `docs/DESIGN.md`. [[blocks]] says how the blocks are made.

- A block's physical properties read with no world: `block.defaultDestroyTime()`, `getExplosionResistance()`, `defaultMapColor()`, and on `defaultBlockState()`, `getSoundType()`, `requiresCorrectToolForDrops()`, `instrument()` and `getPistonPushReaction()`. A button's `BlockSetType` and pressed ticks, and a plate's type, are private fields, read by reflection with vanilla's stone button as the control.
- What a block drops: `Block.getDrops(state, level, pos, null, null, tool)`, with an iron pickaxe and one enchanted with Silk Touch; a slab's double state gives 2.
- What Caramel ships under `assets/` is read from its mod container, as `sounds.json` is (above); `everyNewBlockAndItemShipsItsAssetDefinitions` fails when a provider writes a file under `assets/minecraft/` besides the names.

## Testing what a click sends

- `helper.useBlock` and a mock player reach neither the game's rule that a block's own right click comes first nor anyone's connection. `player.gameMode.useItemOn(...)` is the game's own handling, Fabric's block-click event included. It needs a `ServerPlayer` whose `connection` is set: constructing a `ServerGamePacketListenerImpl` over `new Connection(PacketFlow.SERVERBOUND)` sets it, and goes nowhere.
- Sounds and particles only go to players on the server's player list (`PlayerList.broadcast`, `ServerLevel.sendParticles`). `helper.makeMockServerPlayerInLevel` adds one. Constructing a listener subclass that overrides `send(Packet)` then keeps what it is sent. `ChiselPiecesGameTest.aClickSendsItsSoundsAndParticlesToPlayers` does this for a clicker and another player, and removes both within the same tick, so no other test meets them. That method is deprecated for removal in 26.3 and compiles with a warning.
- Calling a listener's own prediction proves nothing about the listener. With `carveWhileScraping` and `CarvingParticles.onUseBlock` unregistered, every test that read `extraSound` or `burst` still passed; the packet test failed 3 of 32 for the sound alone.

## Traps

- **A mock player's speed ignores Efficiency unless the test applies the stack's modifiers, silently.** With the two `forEachModifier` lines taken out of `ChiselGameTest.miningSpeed`, every tier's check still passed at every level, because neither the Chisel nor the vanilla tool got the bonus. Only the test's own guard failed: "Efficiency V does not speed up a vanilla iron pickaxe held by the mock player".

- **The `gametest` source set compiles and runs against the client classes, silently.** Loom hard-codes the client dependency: `FabricApiTesting.configureTests` passes `true` to `FabricApiAbstractSourceSet.configureSourceSet`, which adds the `client` source set when source sets are split (Loom 1.18.2), and `runGameTest`'s classpath holds `minecraft-clientOnly` and the client output. A server test that calls `net.minecraft.client.Minecraft.getInstance()` compiles, gets `null` and passes (scratch copy). The split-source-set guard in [[build]] does not cover it.
- **A test filter with no namespace matches nothing and exits 255.** The filter is a `/test`-style selector, and one with no colon gets `minecraft:` prepended (`ResourceSelectorArgument`), so `*fuel*` matches no Caramel test. The server logs WARN "Test selection matcher (*fuel*) found no tests" and exits 255, the same code as a data-pack load failure (scratch copy). Write `caramel-gametest:*fuel*`.
- **A fresh run directory logs an ERROR** "Failed to load properties from file: server.properties" with a `NoSuchFileException`, and a WARN "Failed to load eula.txt". Both are first-run noise. A CI checkout has no `build/run/gameTest`, so CI runs show them (CI run log).
- **A float compared as JSON never equals the same number read from a file.** Gson's `JsonPrimitive.equals` compares non-integral numbers by `doubleValue()`, so a codec-encoded `0.05F` (0.0500000007...) differs from a file's parsed `0.05`, and a test comparing a loaded trade with vanilla's file fails on every trade (`shepherdsSellTwentyCarpets` did, reproduced). Decode the file with the same codec and encode it again before comparing.
- **A test class left out of the `fabric-gametest` entrypoints runs none of its tests, silently.** Fabric finds tests only through the entrypoint list in `src/gametest/resources/fabric.mod.json`. With `WallsRecipeGameTest`'s entry removed, the build passed with "All 62 required tests passed" instead of 69, and no log line named the class (in place, then restored). A static reference from another test, such as `VanillaOverridesGameTest` reading `WallsRecipeGameTest.SCOPE`, still runs. Compare the count in "All N required tests passed" with the number of `@GameTest` methods plus `minecraft:always_pass`.
- **`report` lists only the first 20 failure lines, silently.** Lines past `LISTED_FAILURES` (20) count in N and are not shown: "39 of 195 button grids failed" listed the 13 jungle button grids and 7 of the oak ones, and none of the polished blackstone button's 13 (run log). Account for each batched break in N.
- **26.3's `ItemTags` has no constant for some item tags the data holds.** `data/minecraft/tags/item/` holds `stairs.json`, `slabs.json`, `fences.json`, `doors.json`, `trapdoors.json` and `buttons.json`, and `ItemTags.FENCES` fails to compile with "cannot find symbol ... variable FENCES" (`javap` on `ItemTags` lists `WOODEN_STAIRS`, `WOODEN_SLABS`, `WOODEN_FENCES`, `FENCE_GATES`, `WOODEN_DOORS`, `WOODEN_TRAPDOORS`, `WOODEN_BUTTONS` and `WALLS`, and none of `STAIRS`, `SLABS`, `FENCES`, `DOORS`, `TRAPDOORS` or `BUTTONS`; `BlockTags` has all of them). No item tag holds every pressure plate: `#minecraft:wooden_pressure_plates` (`ItemTags.WOODEN_PRESSURE_PLATES`) holds the wooden ones only (`data/minecraft/tags/item/`). `StairsRecipeGameTest` and `SlabsRecipeGameTest` build their item tag with `TagKey.create(Registries.ITEM, ...)`. `MorePerCraft.Scope` takes block tags (`List<TagKey<Block>>`), `BlockTags.WALLS` included. `PressurePlatesAndCarpetsGameTest` checks a pressure plate's block against `BlockTags.PRESSURE_PLATES` and a wool carpet against `ItemTags.WOOL_CARPETS`.
- **`GameTestHelper.assertionException(String, Object...)` garbles its message silently.** It passes the string to `Component.translatableEscape` as a translation key: arguments fill only `%s` placeholders, and a stray `%` drops them all. "PROBE2 {} and %s" with "A", "B" printed "PROBE2 {} and A" (scratch copy). Build messages with `Component.literal`.
- **A test class that looks up an item in a static field can get `minecraft:air`, silently.** Game test classes load before `Chisels.register()` runs if they are named first, and the lookup gives air with null components. `ChiselPiecesGameTest.ironChisel()` looks the Chisel up when a test runs.
- **A pressure plate or button set with no support turns to air when the Chisel's change recomputes it.** `transformBlock` runs `Block.updateFromNeighbourShapes`, so a test needs the ground under a plate and the wall behind a button.
