# CI

`.github/workflows/build.yml` runs `./gradlew build` on GitHub Actions and keeps the jars as a downloadable artifact. Standard runners cost nothing in a public repository ([[github]], "Actions allowance"); the triggers and the cache keep runs short so contributors get quick feedback.

## When it runs

- On a push to `main`, and on every pull request (`on.push.branches` and `on.pull_request`). A pull request branch is built through `pull_request` only; its pushes do not start a second run.
- Only the push trigger sets `paths-ignore: '**.md'`. GitHub checks the files changed by the whole push, not commit by commit (GitHub docs, "Workflow syntax for GitHub Actions"). A push to `main` that changes only Markdown starts no run. A pull request always runs the full build, a docs-only one included.
- `concurrency` with `cancel-in-progress: true` cancels the older run when a newer run starts for the same branch or pull request.

## What it does

- Validates the Gradle wrapper, installs Microsoft's JDK 25, and runs `./gradlew build`, with a 30-minute job timeout. `build` includes the server game tests (`check` depends on `runGameTest`; see [[gametest]]), and the build step's log reports "All N required tests passed".
- `gradle/actions/setup-gradle` with `cache-provider: basic` saves and restores `~/.gradle/caches`, which holds Loom's shared cache, and `~/.gradle/wrapper`. Those paths are fixed, so Loom's per-project `.gradle/loom-cache` is rebuilt on every run. Only runs on `main`, the default branch, write the cache; pull request runs only read it (gradle/actions `docs/setup-gradle.md`, "Using the cache read-only"), and their logs print `cache-read-only: true` and "Entry not saved: cache is read-only". Basic caching removes no stale entries (same file, "Basic Caching" and "Limitations").
- The cache key is `setup-java-Linux-x64-gradle-<hash>`, hashed over `**/*.gradle*`, `**/gradle-wrapper.properties` and the other files that `docs/setup-gradle.md`, "Cache key strategy", lists. Basic caching has no restore keys, so a run restores only an exact key match. A change to one of those files changes the key, so the next run on `main` restores nothing and saves a new entry; a later run with unchanged build files restores it (run logs). GitHub removes an entry not accessed for over 7 days (GitHub docs, "Dependency caching", "Usage limits and eviction policy"), so a run after a quiet week misses with the same key and saves it again.
- The run log shows what the cache did. A miss prints "Basic caching did not find an entry to restore. Will start with empty state." in the "setup gradle" step. A save prints "Basic caching saved entry with key: setup-java-Linux-x64-gradle-..." in "Post setup gradle", whose summary reads "Entries: 0 restored, 1 saved". A restore prints "Cache hit for: <key>" and "Basic caching restored from cache key: <key>" in "setup gradle", and "Post setup gradle" then skips the save ("Save was skipped", "Entries: 1 restored, 0 saved"). `gh api repos/CR4FTEX/caramel/actions/caches` lists the saved entries and their branch.
- After the build it runs `./gradlew runDatagen` and fails the run if `git status --porcelain -- src/main/generated` lists anything. A CI checkout has no `src/main/generated/.cache` (gitignored), so datagen rewrites every file and sweeps stale ones: a provider changed without regenerating, a hand-edited generated file and a hand-placed file all show up (see [[datagen]]). A trial pull request with a hand-edited `en_us.json` failed this step, listing the file and printing "src/main/generated does not match the datagen providers. Run ./gradlew runDatagen and commit the result."; a clean one wrote every file and passed (run logs).
- Uploads `build/libs/` as the artifact `caramel-jar`, kept 14 days, and fails the run if that folder is empty. The artifact holds both jars; [[build]] says which one goes in a `mods` folder. Downloading takes read access (GitHub docs, "Download workflow artifacts") and a sign-in: the API lists an artifact with none, and its `zip` URL answers 401 without one. So in a public repository any GitHub account can fetch each jar for those 14 days.
- A run whose build fails uploads no jar. The upload step has no `if:`, so it takes GitHub's default `success()` and runs only when every step before it passed (GitHub docs, "Expressions", "Status check functions").
- The job's token can only read the repository (`permissions: contents: read`).

## Traps

- **CI checks a hand-made file only where a game test reads it, silently.** CI builds only what is committed, and its datagen step covers `src/main/generated` alone. A texture left uncommitted builds and passes, and that jar draws the missing-texture checkerboard ([[tools]], "Assets"): of the textures, only Smooth Stone's is checked (`StoneFamilyGameTest`; read, not run through CI). The game tests check only the data they cover (see [[gametest]]), and CI does not play the game.
- **A required check must come from a workflow that no path filter can skip.** A workflow skipped by `paths-ignore` reports nothing, so a required `build` check ([[github]], "Protecting `main`") leaves a pull request "Waiting for status to be reported" for ever (GitHub docs, "Troubleshooting required status checks"). That is why the pull request trigger has no `paths-ignore`.
