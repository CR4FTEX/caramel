# Items, tools and right-click block changes

How Caramel adds an item, and how a tool's mining, attack, right click, cooldown, particles and sounds are built from data components in Minecraft 26.3. The code is `io.github.cr4ftex.caramel.item.Chisels`, with the datagen providers `CaramelBlockTransformerProvider`, `CaramelItemTagProvider`, `CaramelModelProvider`, `CaramelLanguageProvider` and `CaramelSoundsProvider`; the decisions behind them are in idea C-009 in `docs/DESIGN.md`. Read in the decompiled 26.3 classes and checked in the game tests `ChiselGameTest` and `ChiselRecipesGameTest` (see [[gametest]]).

## Registering an item

- An item is `Registry.register(BuiltInRegistries.ITEM, key, new Item(properties.setId(key)))`, with `key` a `ResourceKey<Item>`. The constructor reads the id from the properties (`Item.Properties.itemIdOrThrow`), so `setId` comes first. Vanilla's `Items.registerItem` does the same two steps and is private.
- Fabric keeps the built-in registries writable while mods initialize and freezes them right after (`BootstrapMixin.delayRegistryFreeze` in `fabric-registry-sync-v0`). `Chisels` creates its items in static fields, and `Caramel.onInitialize` loads the class by calling `Chisels.register()`.
- A tool needs no class of its own. `Item.useOn`, mining and attacking all read components, so every Chisel is a plain `Item`.
- Registering an entry outside the `minecraft` namespace marks that registry as modded, and Fabric's registry sync then sends its id map to each client that joins (`MappedRegistryMixin.onChange`, `RegistrySyncManager.configureClient`). The Chisels are Caramel's first registered entries.

## What makes an item a tool

- `Item.Properties.pickaxe`, `axe`, `hoe` and `shovel` all call `ToolMaterial.applyToolProperties`. It sets the durability (`max_damage`, with a stack size of 1), `repairable` from the tier's item tag, `enchantable` from the tier's value, a `tool` component, `attribute_modifiers` for attack damage and attack speed, and a `weapon` component.
- `ToolMaterial` is a public record: the tier's `incorrect_for_<tier>_tool` block tag, durability, speed, attack damage bonus, enchantability and repair item tag. Its 7 constants are WOOD (59, 2.0), STONE (131, 4.0), COPPER (190, 5.0), IRON (250, 6.0), DIAMOND (1561, 8.0), GOLD (32, 12.0) and NETHERITE (2031, 9.0). `Chisels.FLINT` is built from WOOD's own values with the repair tag `caramel:flint_tool_materials`, because no vanilla item tag holds flint.
- The `tool` component is a list of rules, a default speed of 1.0, 1 durability per block mined, and a flag for breaking blocks in creative. A vanilla tool has two rules: `deniesDrops(#incorrect_for_<tier>_tool)`, then `minesAndDrops(#mineable/<tool>, speed)`. Both lookups, the speed and whether the block drops, take the first rule that answers (`Tool.getMiningSpeed`, `Tool.isCorrectForDrops`).
- A tool can carry several `minesAndDrops` rules. A Chisel carries one for `#minecraft:mineable/axe` and one for `#minecraft:mineable/pickaxe`. The two tags hold 304 and 542 blocks and share none (resolved from `data/minecraft/tags/block/mineable/`).
- A player's base attack damage is 1 and base attack speed 4. A tool adds `attack_damage` (its baseline plus the tier's bonus) and `attack_speed`, in the main hand, under the ids `Item.BASE_ATTACK_DAMAGE_ID` and `Item.BASE_ATTACK_SPEED_ID`. Every vanilla hoe's damage modifier sums to 0, so every hoe deals 1, half a heart. Hoe attack speeds are 1 for wood and gold, 2 for stone and copper, 3 for iron, and 4 for diamond and netherite (`Items`).
- The `weapon` component is `Weapon(itemDamagePerAttack, disableBlockingForSeconds)`. Vanilla's tools take 2 durability per attack; an axe disables a shield for 5 seconds and the other tools for 0 (`Item.Properties.axe`, `tool`).
- Which enchantments an item takes is decided by item tags: Efficiency reads `#minecraft:enchantable/mining`, Fortune and Silk Touch `enchantable/mining_loot`, Unbreaking and Mending `enchantable/durability`, and Curse of Vanishing `enchantable/vanishing`, which holds the durability tag. Sharpness, Smite and Bane of Arthropods read tags that hold `#minecraft:axes` and not the pickaxes (`data/minecraft/enchantment/`, `data/minecraft/tags/item/enchantable/`). An enchanting table also needs the `enchantable` component.
- Three more item tags carry tool traits: `#minecraft:cluster_max_harvestables` gives the full amethyst cluster drop and lists the 7 pickaxes by name, `#minecraft:breaks_decorated_pots` holds the tool tags, and `#minecraft:piglin_loved` lists the golden tools by name.
- A tag file adds to the same tag in other packs, so Caramel's `data/minecraft/tags/item/enchantable/mining.json` holds only `#caramel:chisels` and replaces nothing (`TagLoader.load`). `ChiselGameTest.chiselsTakeThePickaxesEnchantmentsAndTraits` compares every enchantment and each of the three trait tags with the tier's pickaxe.

## Mining speed

- A block's progress per tick is the player's speed, divided by the block's hardness, divided by 30 when the held tool is correct for drops or the block needs none, and by 100 otherwise (`BlockBehaviour.getDestroyProgress`).
- `Player.getDestroySpeed` starts from the held stack's speed for the block. Only when that is above 1.0 does it add the `mining_efficiency` attribute. Then it multiplies by Haste, by Mining Fatigue and by the `block_break_speed` attribute, and divides by 5 when the player is off the ground.
- Efficiency is that attribute and nothing else: `add_value` of the level squared plus 1 on `minecraft:mining_efficiency` in the main hand, so +26 at level V (`data/minecraft/enchantment/efficiency.json`).
- So half a tool's rule speed is half the mining speed only without Efficiency. At Efficiency V an iron pickaxe mines at 6 + 26 = 32, and a tool with rule speed 3 at 29.
- A Chisel has half its tier's rule speed and an item modifier of its own on the same attribute: `caramel:chisel_mining_efficiency`, `add_multiplied_total` -0.5, main hand. That halves Efficiency's bonus too, so its speed is half the tier's pickaxe or axe at every level. Blocks neither tool mines keep the default speed of 1.0, a bare hand's.
- Half of the wood tier's 2.0 is 1.0, the bare hand's speed, and the game adds Efficiency only above 1.0. The flint tier's rule speed is `Math.nextUp(1.0F)`, the smallest float above 1.0, which keeps the hand's pace and lets Efficiency count (`Chisels.miningSpeed`).
- `ChiselGameTest.chiselsTakeTwiceAsLongAtEveryEfficiencyLevel` checks this as a player's speed, for every tier at Efficiency 0 to V.

## Right-click block changes

- What an axe, a hoe or a shovel does to a block on a right click is data: the registry `minecraft:block_transformer`, with the three entries `axe`, `hoe` and `shovel` (`data/minecraft/block_transformer/`). It is a data-pack registry loaded with the world and sent to clients, and `/reload` does not reload it (`RegistryDataLoader.WORLD_REGISTRIES`, `SYNCHRONIZED_REGISTRIES`).
- An item names one transformer in its `minecraft:block_transformer` component, and `Item.useOn` runs it. `Item.Properties.axe` adds the component with `delayedComponent(DataComponents.BLOCK_TRANSFORMER, context -> context.getOrThrow(BlockTransformers.AXE))`.
- A transformer is a list of entries. `BlockTransformer.transformBlock` tries them in order and uses the first whose `block_state_provider` gives a block for the clicked position. It then sets the block, plays the entry's sound, sends its particles and takes `item_damage_per_use` durability. The codec's default for that is 0 and the Java builder's is 1.
- `transformBlock` does nothing when the item is in the main hand, the off hand holds an item that blocks attacks, and the player is not sneaking.
- Vanilla's `minecraft:axe` has 7 entries: stripping, with 25 rules whose `copy_properties` keeps the log's direction, then 3 for scraping oxidation and 3 for removing wax (`BlockTransformers.bootstrap`). An item that names `minecraft:axe` gets all 7.
- The Chisel strips and does not scrape or unwax, so it has a transformer of its own, `caramel:chisel`, generated by `CaramelBlockTransformerProvider`. Its first entry is the axe's stripping entry, copied at datagen from the registry lookup that vanilla's own data is generated from. Datagen stops unless the axe transformer has exactly 1 entry with the stripping sound.
- The owner's cycles follow as three more entries: stone with Caramel's carving sound (see "Sounds"), wood with the stripping sound, and moss with the game's moss break. A block's rule is `matching_blocks` of one block giving the next block's default state, so a click advances one step. A piece's rule uses `copy_properties`, as vanilla's stripping does, so stairs, slabs, walls, buttons and plates keep their state; `transformBlock` then runs `Block.updateFromNeighbourShapes` and sets the block with neighbour updates, so a wall's sides and a stair's shape stay right. The cycles are one list per family in `CaramelBlockTransformerProvider.STONE_CYCLES` and `WOOD_CYCLES`. A way in (`STONE_WAYS_IN`, C-010) is one more rule, from a block outside every cycle into one, which no cycle returns to: Smooth Stone into Polished Stone. The pieces are derived, not listed (`pieceLoops`, `pieceWaysIn`, `pieceMoss`, C-010): each kind in `CaramelBlockFamilies.PIECES` is taken from each member of a line through `CaramelBlockFamilies.piece`, which reads vanilla's `BlockFamilies` and Caramel's together, skipping a member without it; two or more make a loop. So a new line, way in or `MOSS_SCRAPING` entry gets its pieces with no new code once its family is declared. A kind outside `PIECES`, such as a fence, gets no rule, silently; today no line holds two fences. Datagen stops on a block that starts two rules, on a piece pair whose properties differ, on a mossy piece with no clean one, on a way in that starts inside a cycle or leads outside them, and on a block with block state properties, which a rule would reset, unless it is in `RESET_TO_DEFAULT`: the Chiseled Stone Pillar's axis, which the owner chose to lose, so a Chisel-made pillar stands upright. A rule's `then` names the target's default state with its properties written out, such as `axis: y`.
- A mod's pack loads its own entries of this registry: `data/caramel/block_transformer/chisel.json` is `caramel:chisel`. `ChiselGameTest.chiselsStripLikeAxesAndCycleTheOwnersBlocks` reads it from the registry and, for every block in the game, compares what it gives with the axe's stripping entry and the owner's cycles.
- A Chisel's component is `delayedComponent(DataComponents.BLOCK_TRANSFORMER, context -> context.get(Chisels.TRANSFORMER).orElse(null))`. Delayed components are resolved wherever item components are built: on a server at data load (`ReloadableServerResources.loadResources`), and on a client at every join, against the registries that server sent (`RegistryDataCollector.updateComponents`). Datagen never builds them.
- A delayed component that returns null is left off the item (`DataComponentMap.Builder.setUnchecked`). A server without Caramel sends no `caramel:chisel`, so there a client's Chisels have no right click. Vanilla's own tools use `getOrThrow`, which throws "Missing element" in that case; on a client that ends the join (`ClientCommonPacketListenerImpl.onPacketError`). The join was read in the decompiled classes; no client was run. The owner chose the lenient lookup (`docs/DESIGN.md`, C-009).
- A held right click repeats every 4 ticks (`Minecraft.startUseItem` sets `rightClickDelay` to 4, and `handleKeybinds` fires again while the key is down). Vanilla's transformers run out of steps, and the Chisel's cycles never do, so without a cooldown holding the button on a cycle block advances 5 steps a second. A click is offered to the main hand first, so a main-hand Chisel that changes the block ends the click before the off hand's item is used. Read in the decompiled client classes.
- Fabric API's `BlockTransformerHelper.registerStripping` adds to vanilla's `minecraft:axe` only, so a log another mod registers there does not reach `caramel:chisel`.

## Cooldowns

- The `use_cooldown` component, `UseCooldown(seconds, cooldownGroup)`, starts an item cooldown of `seconds * 20` ticks (`UseCooldown.ticks`). `ItemStack.useOn` starts it after a block click whose result is a `Success` with `wasItemInteraction()`, which `BlockTransformer.transformBlock` returns when it changed a block, and `PASS` otherwise (`ItemStack.applyAfterUseComponentSideEffects`). Each Chisel carries 1 second in the group `caramel:chisel`.
- A cooldown belongs to a group, the component's `cooldown_group` or else the item's id (`ItemCooldowns.getCooldownGroup`), so every item in one group waits together.
- While an item cools down, `MultiPlayerGameMode.useItemOn` and `ServerPlayerGameMode.useItemOn` skip its `useOn` and return `PASS`, and their `useItem` refuses it too. `Minecraft.startUseItem` ends its loop over the hands only on a `Success` or a `Fail`, so on a `PASS` it offers the click to the off hand, and an off-hand block or torch is placed. In the 26.3 jars `ItemCooldowns.isOnCooldown` is called only by those two game-mode classes and by `ServerGamePacketListenerImpl`, for block items and buckets (call sites searched with `javap`), so mining and attacking never wait.
- The hotbar and inventory draw the cooldown as a white sweep over the item (`GuiGraphicsExtractor`, through `ItemCooldowns.getCooldownPercent`), which the `minecraft:cooldown` item model property also reads.
- A server player's cooldowns send each start and end to its client (`ServerItemCooldowns`, through `player.connection`); a plain `Player` keeps them locally (see [[gametest]]). The client starts its own copy when it predicts the change, and starts it over when the server's start packet arrives (`ClientPacketListener.handleItemCooldown`, `addCooldown`), at least a tick later, so its copy ends after the server's unless the server's end packet clears it first.
- Fabric's `UseBlockCallback` runs before the game's own handling of a block click, on both sides (`MultiPlayerGameModeMixin`, `ServerPlayerGameModeMixin` in `fabric-events-interaction-v0`). Anything but `PASS` is the click's result; on the client, only a result that consumes the action is sent to the server, so a `FAIL` sends nothing and ends `startUseItem`'s loop over the hands. `Chisels.holdWhileWaiting` answers `FAIL` for a waiting Chisel on a block its right click would change, checking with `RightClickChanges.change` what `ItemStack.useOn` and `transformBlock` check first: adventure mode, an off-hand item that blocks attacks while the player does not sneak, and each entry's faces and rules.
- With that, a held click carves every 1 to 1.2 seconds in singleplayer: the repeat comes every 4 ticks, and the client's copy of the wait ends a tick or so after the server's (reasoned from the classes above; not timed in game).
## Particles

- Breaking a block throws, for each box of its shape, at least 2 and one per quarter block along each side, so 4 by 4 by 4, 64, for a full block (`ClientLevel.addDestroyBlockEffect`, through level event 2001, which also plays the break sound).
- A transformer entry's `particle` is only `none`, `scrape`, `wax_on` or `wax_off` (`BlockTransformer.TransformParticle`), so no data file can ask for break particles.
- `ServerLevel.sendParticles` sends to every player in range, with no player left out. With `ClientboundLevelParticlesPacket.RandomizationType.ALTERNATIVE`, the client places each particle at the given corner plus a uniform random share of the spread, so a corner and a spread of 1.0 fill the block evenly (`ClientPacketListener.handleParticleEvent`). Each particle then gets its own random burst in `Particle`'s constructor, as break particles do, so a speed of 0 still bursts.
- A mined block's cracks appear 0.1 out from the face being hit and 0.1 in from its edges (`ClientLevel.addBreakingParticles`). Particles that start inside a block that stays solid are not stopped by it, since a collision scan starts past the box's own edge, but a solid neighbour stops and freezes them unseen (`VoxelShape.collideX`, `Particle.move`; read in the decompiled classes, not seen in game).
- `ClientLevel.addParticle` drops particles by the player's Particles setting, unless sent with `alwaysShow`; break particles go straight to the particle engine and are never dropped.
- `CarvingParticles` sends `minecraft:block` particles of the block as it was, or of the Moss Block when scraping moss, from the server, a quarter of what breaking that shape throws (16 for a full block, 8 for a bottom slab, 2 for a button), over the clicked side of the block's shape where a mined block's cracks appear, for every change a Chisel makes and for an axe's stripping. The game offers no event after a block transformer's change, so it sends them from Fabric's `UseBlockCallback`, just before the change in the same tick. `RightClickChanges.change` works out the entry the click will run by the checks `ItemStack.useOn` and `transformBlock` make first, and by the game running a block's own right click first; the item's cooldown is left to the caller. `ChiselGameTest.chiselsAndAxesThrowParticlesExactlyWhenTheyChiselOrStrip` checks the prediction against what a `helper.useBlock` click on every block then changes, and reads the `CarvingParticles.Burst` it would send. `ChiselPiecesGameTest.aClickSendsItsSoundsAndParticlesToPlayers` sees the packets themselves, for a real click (see [[gametest]]).

## Assets

- An item needs an item definition `assets/caramel/items/<id>.json`, a model `assets/caramel/models/item/<id>.json`, a texture and a name in `assets/caramel/lang/en_us.json`. `CaramelModelProvider` writes the first two with `ItemModelGenerators.generateFlatItem(item, ModelTemplates.FLAT_HANDHELD_ITEM)`, the call vanilla uses for its tools, and `CaramelLanguageProvider` the names. All of it lands in `src/main/generated/assets/caramel/`.
- Textures are never generated: they come from the owner or an artist and go in `src/main/resources/assets/caramel/textures/item/` (`docs/TEXTURES.md`, `CLAUDE.md`, "Art"). A model names its texture and datagen does not look for the file (`ModelTemplate.create`).
- A model whose texture file is missing is drawn with the game's missing sprite, a 16 by 16 magenta and black checkerboard (`MaterialBaker`, `MissingTextureAtlasSprite`). Each resource load then logs a WARN per model, "Missing textures in model caramel:item/<id>:" (`MaterialBaker.logMissingTextures`, read in the decompiled client classes).
- A tooltip lists an item's modifiers under "When in Main Hand:". A negative `add_multiplied_total` modifier shows as a red percentage, so each Chisel shows "-50% Mining Efficiency" (`ItemAttributeModifiers.Display.Default.apply`, lang keys `attribute.modifier.take.2` and `attribute.name.mining_efficiency`). Efficiency's own line still shows its whole bonus.

## Sounds

- A transformer entry names one sound event and no volume or pitch: `transformBlock` plays it with `level.playSound(player, pos, sound, SoundSource.BLOCKS, 1.0F, 1.0F)` (`BlockTransformer.BlockTransformData.CODEC`). A sound at another pitch needs an event of Caramel's own.
- A sound event is registered like an item, while the mod initializes: `Chisels.CARVE_STONE` is `Registry.registerForHolder(BuiltInRegistries.SOUND_EVENT, id, SoundEvent.createVariableRangeEvent(id))`, `caramel:item.chisel.carve_stone`. A transformer file names it by id, `"sound": "caramel:item.chisel.carve_stone"`.
- What an event plays is client data, `assets/<namespace>/sounds.json`, keyed by the event's path. `CaramelSoundsProvider`, a `FabricSoundsProvider`, writes Caramel's into `src/main/generated/assets/caramel/sounds.json`. Fabric's builder stops datagen, "Failed to run data generation", on an entry that names an unregistered event ("Referenced sound event caramel:nope does not exist") or a pitch outside 0.5 to 2 ("Sound pitch must be between 0.5 and 2 (inclusive)"), both reproduced (`SoundTypeBuilderImpl`).
- An entry of `"type": "event"` plays one of the named event's sounds, with its volume multiplied by the entry's and its pitch by the entry's (`SoundManager.Preparations`, read in the decompiled client classes). Vanilla's parrots imitate mobs this way: `entity.parrot.imitate.blaze` plays `entity.blaze.ambient` at pitch 1.8 (vanilla's `sounds.json`, from the asset index). The anvil's `block.anvil.use` plays `random/anvil_use` at volume 0.5, and the carving sound's entry has volume 0.5 and pitch 1.5, so it plays that file at volume 0.25 and pitch 1.5. The anvil block plays it at a random pitch from 0.9 to 1.0 (`LevelEventHandler`, event 1030).
- Naming the event rather than its file keeps a resource pack's anvil sound in the carving sound too. A sound file of Caramel's own is an `.ogg` in `assets/caramel/sounds/`, which an entry names with `RegistrationBuilder.ofFile` (`docs/TEXTURES.md`, "Where files go").
- The client finds an event's definition by the event's own `location()`, not by its registry key (`AbstractSoundInstance`, `SoundManager.getSoundEvent`), and `FabricSoundsProvider` keys a `Holder` by its registry key. `SoundEvent` is a record that holds its location apart from the key, so `Chisels.registerSound` builds both from one id.
- The subtitle is the playing event's own, never the borrowed event's: each definition is loaded with `new WeighedSoundEvents(location, registration.getSubtitle())`. Caramel's is its own key, `subtitles.caramel.item.chisel.carve_stone`, which `CaramelLanguageProvider` translates as "Block chiselled".
- A server has no sound manager and never reads `sounds.json`. `ChiselGameTest.carvingStoneSoundsLikeAHigherPitchedAnvil` reads the file from Caramel's mod container instead (see [[gametest]]), and checks that every sound event Caramel registers sits at its own id and has a definition, and that nothing else does.

## Traps

- **With the lenient lookup, a missing block transformer file is silent in game.** Every Chisel loads with no right click. Only the game tests fail, reproduced by deleting `src/main/generated/data/caramel/block_transformer/chisel.json`: "caramel:flint_chisel has the right-click transformer null, expected caramel:chisel" for each of the 7, and "Unknown internal error: Missing element ResourceKey[minecraft:block_transformer / caramel:chisel]" from the test that reads the transformer.
- **With `getOrThrow`, as vanilla's tools use, the same missing file stops every world from loading.** The data packs fail with WARN "Failed to load vanilla datapack, bit oops" and `IllegalStateException: Missing element ResourceKey[minecraft:block_transformer / caramel:chisel]`, and the game test server exits (reproduced the same way, before the lookup was made lenient).
- **An item class first touched after mod initialization cannot register its items.** With `Chisels.register()` taken out of `Caramel.onInitialize`, the first datagen provider to name `Chisels` loads the class too late: "Failed to run data generation", caused by `ExceptionInInitializerError` and `IllegalStateException: Registry is already frozen`.
- **A tag entry that does not resolve drops the whole tag, vanilla's included.** In a game test run without the Chisels registered, the log shows "Couldn't load tag caramel:chisels as it is missing following references: caramel:flint_chisel (from caramel), ...", then the same line for each of the 5 vanilla tags that hold `#caramel:chisels` (`breaks_decorated_pots`, `cluster_max_harvestables`, `enchantable/durability`, `enchantable/mining`, `enchantable/mining_loot`), for `enchantable/vanishing`, which holds the durability tag, and for `piglin_loved`, which names `caramel:golden_chisel`. The data packs then fail to load: "Failed to parse minecraft:efficiency from pack vanilla", caused by "Missing tag: 'minecraft:enchantable/mining' in 'minecraft:item'", and the same for Fortune, Silk Touch, Unbreaking, Mending and Curse of Vanishing. A file under `data/minecraft/tags/` may name only what Caramel always registers.
- **An anvil in creative ignores which items an enchantment fits, silently.** `AnvilMenu.createResult` treats a book's enchantment as fitting the item when the player `hasInfiniteMaterials()`, so in creative a Sharpness book goes onto a Chisel, and onto a pickaxe too. It still refuses a book that clashes with an enchantment the item has (`Enchantment.areCompatible`). Creative also skips the level cost, the cap at 40 levels and the chance of damaging the anvil. The enchanting table and `/enchant` keep the item's rules in every mode (`EnchantmentMenu`, `EnchantCommand`). The owner's first C-009 playtest met it. Check what an anvil allows in survival; `ChiselGameTest.anAnvilPutsOnlyThePickaxesBooksOnAChiselInSurvival` runs both modes.
- **A block with its own right click never reaches the Chisel on a plain click, and the block-click listeners run anyway.** The game runs the block's use first unless the player sneaks with something in hand (`ServerPlayerGameMode.useItemOn`, `MultiPlayerGameMode.performUseItemOn`). Among the blocks a Chisel changes, only buttons have one, and `RightClickChanges` knows it. Left out, a plain click on a button threw particles and played the moss sound for a change that never happened, and a waiting Chisel could not press it (deliberate break). `ChiselPiecesGameTest` fails if any other changeable block declares `useWithoutItem` or `useItemOn` below `BlockBehaviour`, which a fence would.
- **`copy_properties` on a pressed button or plate leaves it pressed for good, silently.** The tick that releases it is scheduled for the block it was, and `ServerLevel.tickBlock` runs a tick only while the position still holds that block. Reproduced: a pressed Smooth Stone Button and plate, changed by the raw transformer, were still pressed 25 ticks later. A rule's predicate cannot be told to skip them, so `Chisels.refuseWhilePowered` ends the click, for a Chisel only: an axe on a powered copper door or bulb must stay the game's, and with the limit taken off, `anAxeStillScrapesPoweredCopper` failed 3 of 3.
- **A registered sound event with no definition plays nothing.** At every resource load the client logs WARN "Missing sound for event: <id>" (`SoundEngine.reload`, run from `SoundManager.apply`). Each play after that is silent and logs nothing more: "Unable to play unknown soundEvent" in `SoundEngine.play` is only for ids the registry does not hold. Read in the decompiled client classes. `carvingStoneSoundsLikeAHigherPitchedAnvil` fails when `sounds.json` lacks one of Caramel's registered events.
- **A cooldown alone lets the server carve without the player hearing it, silently.** Without `holdWhileWaiting`, a held click that lands after the server's wait ends but before the client's is refused by the client, which returns `PASS` but still sends the click (`MultiPlayerGameMode.startPrediction`), and the server carves. `transformBlock` plays the sound with the player left out, as the client already played it (`level.playSound(player, ...)`, `ServerLevel.playSeededSound`), and the server sends no swing for a predicted action, so the player gets neither. The client also offers that click to the off hand. Two reviewers found it in the decompiled classes; it was not reproduced in game.
- **A subtitle key with no translation is silent.** The subtitles overlay shows the key itself. `SoundManager.apply` logs ERROR "Missing subtitle <key> for sound event: <id>" only when `SharedConstants.IS_RUNNING_IN_IDE` is true, and nothing in Minecraft, Fabric Loader or Fabric API sets that field (read in the decompiled classes, and the field's only writes searched with `javap`). `carvingStoneSoundsLikeAHigherPitchedAnvil` checks its one subtitle with `Language.getInstance().has`.
- **A tool rule with a speed of exactly 1.0 ignores Efficiency, silently.** With the flint tier at a plain half of wood's 2.0, `chiselsTakeTwiceAsLongAtEveryEfficiencyLevel` printed "40 of 504 Chisel mining speed checks failed": the flint tier's 8 mined blocks at each of Efficiency I to V. The rule's speed has to be above 1.0 for the attribute to count (`Player.getDestroySpeed`).
- **Halving a tool's rule speed alone stops halving its mining speed once it is enchanted, silently.** Efficiency's bonus is added whole. With the Chisel's modifier on `mining_efficiency` set to -0.25, the same test failed 280 of 504 checks, every tier at Efficiency I to V.
